# Регламент: узел релея

Что делать в конкретной ситуации. Каждая процедура заканчивается ЗАМЕРОМ —
операция считается выполненной только после того, как факт подтверждён.

Доступ: `ssh -i ~/.ssh/z2k_vps_ed25519 root@213.176.74.63`. Только по ключу.

## Прежде чем трогать что-либо

```
sh vps/bin/verify.sh
```

Расхождение означает, что кто-то правил файл прямо на машине. Сперва решается,
чья версия верна, и только потом раскатывается. Раскатка поверх расхождения
затирает чужую работу молча.

Одно расхождение сейчас ожидаемо и держится открытым намеренно: `--admin-token`
виден в `/proc/<pid>/cmdline`. Убирается только в окно перезапуска релея.

## Раскатить правку конфигурации

```
sh vps/bin/deploy.sh            # посмотреть, что изменится
sh vps/bin/deploy.sh --apply    # раскатать
```

Скрипт делает резервную копию, проверяет конфиг (`nginx -t`, `caddy validate`),
перезагружает **без разрыва соединений** и сам прогоняет сверку после. Если
проверка не прошла — возвращает прежний файл и выходит с ошибкой.

Файлы с секретами (`z2k-relay.service` и его drop-in) лежат в репозитории с
маской `<СЕКРЕТ>` и НЕ раскатываются: они там ради сверки структуры.

## «Узел недоступен», жалобы на подключение

```
sh vps/observability/collect.sh 120
```

Читается сверху вниз:

- **SYN потеряно > 0** — переполнялась очередь рукопожатий. Смотреть
  «полуоткрытых»: десятки-сотни при малом числе принятых подключений — сканер с
  мёртвых адресов; всплеск принятых подключений — вернулся флот разом (§4
  DESIGN). Лечится разным.
- **очередь приёма переполнена > 0** — уже не ядро, а приложение не успевает
  `accept()`. Смотреть load и RSS релея.
- **syncookies выдано > 0** — всплеск был и был пережит. Это не отказ, это
  сработавший предохранитель. Ничего делать не нужно, но стоит записать время.
- **всё по нулям, а жалобы есть** — проблема не здесь. Идти к клиенту:
  DNS, маршрут, блокировка адреса узла у провайдера.

## Растёт память релея

184 КБ на соединение — норма (замер: 706 МБ на 3820). Тревога, если RSS растёт
при неизменном числе соединений: это утечка, а не нагрузка. Снять
`ss -tn state established '( sport = :8080 )' | wc -l` и RSS дважды с интервалом
в час и сравнить отношение.

## Перезапуск, который рвёт соединения

`systemctl restart nginx` — около 1800 туннелей. Релей — около 3500.

Только в окно и только когда иначе нельзя. Порядок:

1. Предупредить владельца, дождаться подтверждения.
2. Снять число соединений до: `sh vps/observability/collect.sh 30`.
3. Перезапустить.
4. Через 5 минут снять снова: соединения должны вернуться к прежнему уровню.
   Не вернулись — клиенты не переподключаются сами, это отдельная авария.

Reload соединений не рвёт и окна не требует: `nginx -s reload`,
`systemctl reload caddy`.

## Откатить правку

Каждый раскатанный файл оставляет рядом `.z2kbak`:

```
cp /etc/nginx/nginx.conf.z2kbak /etc/nginx/nginx.conf && nginx -t && nginx -s reload
```

Для настроек ядра откат — вернуть файл и `sysctl --system`, затем ОБЯЗАТЕЛЬНО
`sysctl -n <ключ>`: файл может лежать правильный, а значение не примениться
(`/etc/sysctl.conf` применяется последним и перекрывает `sysctl.d`).

## После перезагрузки узла

`z2k-net-tuning.service` поднимает RPS сам (`enabled`). Проверить:

```
sh vps/bin/verify.sh | grep -A1 'разнос приёма'
```

`ВЫКЛЮЧЕН` означает, что юнит не отработал — приём идёт в один поток, узел
держит примерно вдвое меньший всплеск.
