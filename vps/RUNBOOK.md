# Регламент: узел релея

Что делать в конкретной ситуации. Каждая процедура заканчивается ЗАМЕРОМ —
операция считается выполненной только после того, как факт подтверждён.

Доступ: `ssh -i ~/.ssh/z2k_vps_ed25519 root@213.176.74.63`. Только по ключу.

## Прежде чем трогать что-либо

```
sh vps/bin/verify.sh
```

Расхождение означает, что кто-то правил файл прямо на машине. Сперва решается,
чья версия верна, и только потом раскатывается. Раскатка поверх расхождения
затирает чужую работу молча.

Одно расхождение сейчас ожидаемо и держится открытым намеренно: `--admin-token`
виден в `/proc/<pid>/cmdline`. Убирается только в окно перезапуска релея.

## Раскатить правку конфигурации

```
sh vps/bin/deploy.sh            # посмотреть, что изменится
sh vps/bin/deploy.sh --apply    # раскатать
```

Скрипт делает резервную копию, проверяет конфиг (`nginx -t`, `caddy validate`),
перезагружает **без разрыва соединений** и сам прогоняет сверку после. Если
проверка не прошла — возвращает прежний файл и выходит с ошибкой.

Файлы с секретами (`z2k-relay.service` и его drop-in) лежат в репозитории с
маской `<СЕКРЕТ>` и НЕ раскатываются: они там ради сверки структуры.

## «Узел недоступен», жалобы на подключение

```
sh vps/observability/collect.sh 120
```

Читается сверху вниз:

- **SYN потеряно > 0** — переполнялась очередь рукопожатий. Смотреть
  «полуоткрытых»: десятки-сотни при малом числе принятых подключений — сканер с
  мёртвых адресов; всплеск принятых подключений — вернулся флот разом (§4
  DESIGN). Лечится разным.
- **очередь приёма переполнена > 0** — уже не ядро, а приложение не успевает
  `accept()`. Смотреть load и RSS релея.
- **syncookies выдано > 0** — всплеск был и был пережит. Это не отказ, это
  сработавший предохранитель. Ничего делать не нужно, но стоит записать время.
- **всё по нулям, а жалобы есть** — проблема не здесь. Идти к клиенту:
  DNS, маршрут, блокировка адреса узла у провайдера.

## Растёт память релея

184 КБ на соединение — норма (замер: 706 МБ на 3820). Тревога, если RSS растёт
при неизменном числе соединений: это утечка, а не нагрузка. Снять
`ss -tn state established '( sport = :8080 )' | wc -l` и RSS дважды с интервалом
в час и сравнить отношение.

## Перезапуск, который рвёт соединения

`systemctl restart nginx` — около 1800 туннелей. Релей — около 3500.

Только в окно и только когда иначе нельзя. Порядок:

1. Предупредить владельца, дождаться подтверждения.
2. Снять число соединений до: `sh vps/observability/collect.sh 30`.
3. Перезапустить.
4. Через 5 минут снять снова: соединения должны вернуться к прежнему уровню.
   Не вернулись — клиенты не переподключаются сами, это отдельная авария.

Reload соединений не рвёт и окна не требует: `nginx -s reload`,
`systemctl reload caddy`.

## Откатить правку

Каждый раскатанный файл оставляет рядом `.z2kbak`:

```
cp /etc/nginx/nginx.conf.z2kbak /etc/nginx/nginx.conf && nginx -t && nginx -s reload
```

Для настроек ядра откат — вернуть файл и `sysctl --system`, затем ОБЯЗАТЕЛЬНО
`sysctl -n <ключ>`: файл может лежать правильный, а значение не примениться
(`/etc/sysctl.conf` применяется последним и перекрывает `sysctl.d`).

## После перезагрузки узла

`z2k-net-tuning.service` поднимает RPS сам (`enabled`). Проверить:

```
sh vps/bin/verify.sh | grep -A1 'разнос приёма'
```

`ВЫКЛЮЧЕН` означает, что юнит не отработал — приём идёт в один поток, узел
держит примерно вдвое меньший всплеск.

## События, метрики, тревоги (с плана 1 v2)

- События: `/var/log/z2k-relay/events-YYYY-MM-DD.jsonl`, 30 суток. Быстрые срезы:
  `jq -r 'select(.ev=="session_close") | .reason' events-$(date -u +%F).jsonl | sort | uniq -c | sort -rn`
  `jq -r 'select(.ev=="session_close" and .reason=="read_timeout") | .asn' … | sort | uniq -c | sort -rn | head`
- Метрики: `curl -s 127.0.0.1:9098/metrics`; pprof: `go tool pprof http://127.0.0.1:9098/debug/pprof/heap`.
- Тревоги: `systemctl list-timers z2k-alert.timer`, состояние `/var/lib/z2k-relay/alert-state/`, правила в `alert.sh`.
  Секреты `Z2K_ALERT_BOT_TOKEN` и `Z2K_ALERT_CHAT_ID` — в `/etc/z2k/secrets.env`.
- Таблица ASN: `systemctl start z2k-asn-update.service` для ручного обновления; релей подхватывает в течение часа.
- Новые флаги релея (`--events-dir`, `--asn-table`) лежат в drop-in юнита и вступают в силу
  при перезапуске релея — это окно: `systemctl restart z2k-relay` рвёт все туннели.
- Юнит под `ProtectSystem=strict`: писать релей может только в `StateDirectory`
  (`/var/lib/z2k-relay`) и `LogsDirectory` (`/var/log/z2k-relay`). Любой новый путь
  для записи объявляется в drop-in, `chown` не поможет (02.09.2026: релей падал на
  старте, полторы минуты отката).
- Подмена бинарника ТОЛЬКО через `mv` (rename): `cp` поверх работающего файла даёт
  «Text file busy». Порядок: `mv relay.new relay` → drop-in с флагами → `restart`;
  drop-in с новыми флагами раньше бинарника = crash-loop на неизвестном флаге.

## Нагрузочный прогон релея (план 2 v2)

```
cd vps-relay && ulimit -n 20000 && go test -tags load -run TestLoad_3000Sessions -count=1 -v .
```
3000 сессий × 3 стрима против настоящего handleWS в одном процессе. Порог
120 КБ heap на сессию включает поддельный клиент и DC стенда; 02.09.2026
замер дал 79 КБ и p95 кадра 78 мкс. Если число выросло — сначала
`-memprofile` и `go tool pprof -top -sample_index=inuse_space`: 02.09 весь
рост был в буферах чтения, прибитых к стримам.

## Деплой релея без разрыва (с плана 3 v2)

Релей — шаблон `z2k-relay@.service`, экземпляры `a` и `b`; одновременно
работает один. Оба слушают 8445 (TLS за nginx, PROXY-заголовок) и plain-порт
из `/etc/z2k/relay-<i>.env` через reuseport.

```
cd vps-relay && PATH=<go1.25.12>:$PATH sh deploy/build.sh
scp -O vps-relay/z2k-vps-relay root@213.176.74.63:/usr/local/bin/z2k-vps-relay.new
ssh root@213.176.74.63 'cp -p /usr/local/bin/z2k-vps-relay /usr/local/bin/z2k-vps-relay.prev && mv -f /usr/local/bin/z2k-vps-relay.new /usr/local/bin/z2k-vps-relay'
sh vps/bin/deploy.sh --apply              # юнит/скрипты; nginx перезагружается только если менялся
ssh root@213.176.74.63 'sh /opt/z2k-vps/bin/relay-switch.sh'   # поднимает спящий, проверяет, гасит работающий (drain до 120 с)
```
Откат: вернуть `.prev` тем же `mv` и снова `relay-switch.sh`.

- Первая миграция 02.09.2026 со старого одиночного юнита шла на `b` с
  `Z2K_PLAIN_PORT=8081`: старый процесс держал 8080 без reuseport. Экземпляр
  `a` уже с 8080; следующий `relay-switch.sh` вернёт схему в норму.
- `http: TLS handshake error … EOF` в журнале — клиенты и сканеры, закрывшие
  соединение до конца рукопожатия; это не отказ.
- Сертификат: кеш autocert `/var/lib/z2k-relay/acme/213.176.74.63.nip.io`,
  импортирован из caddy 02.09.2026 (годен до 08.11.2026). Продление — сам
  autocert через TLS-ALPN за 30 дней до конца; проверить в начале октября:
  `journalctl -u 'z2k-relay@*' | grep -i acme`.
- caddy выключается отдельным шагом после суток наблюдения (план 3, шаг 8);
  вместе с ним раскатывается `config/nginx-http-z2k.conf` (:8088 и :80).
