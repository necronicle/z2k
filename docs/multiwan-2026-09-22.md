# WAN discovery: main-table defaults and explicit interfaces

Automatic WAN discovery is restricted to the main routing table. It collects
all usable default-route devices, including separate defaults and multiline
ECMP next hops. The same `lib/wan.sh` detector serves firewall installation and
periodic repair. IPv4 and IPv6 are evaluated independently.

An explicit comma/space-separated `WAN_IFACE` list takes priority. A second ISP
that exists only in another connection policy must be listed explicitly; it is
not discovered by scanning every policy table. Main is a routing boundary,
not proof that an interface is a physical ISP: a VPN can be the main default.
The correction therefore does not attempt to classify providers by names or
kernel device types. Only loopback and bridge guards remain.

## Why the earlier change was wrong

A user reported YouTube failing with USB and Wi-Fi providers both enabled.
The old main-table parser already accepted multiple separate defaults. The
subsequent all-table expansion included user VPN defaults as well as possible
secondary ISPs. A blacklist of VPN names/types could not establish the intended
boundary, especially for renamed tunnels or PPP-based connections.

The original USB/Wi-Fi failure has not been reproduced on that user's router.
Restoring main-table discovery fixes the unwanted expansion; it does not prove
that every dual-provider configuration or DPI strategy will work.

The existing `--bind-fix4/6` flags remain: outgoing fake-packet binding and
interface discovery are separate concerns. Other Keenetic builds enable these
flags as well for explicit multiple-interface configurations.

## Repair and migration contract

Additive `start_fw` reconciles z2k NFQUEUE rules in INPUT/FORWARD/POSTROUTING
against a successful nonempty selected set for each family. It removes stale
interface rules, including policy-only Ethernet interfaces, not merely known
VPN names. Queue numbers are matched exactly; native rules and other queues
are preserved. Explicitly selected interfaces remain eligible.

A failed route query or successful empty result defers this cleanup. It never
means every existing rule should be deleted. The next valid nonempty snapshot
allows reconciliation. The self-healer checks required chain/protocol/interface
combinations and skips unavailable families without a restart storm. NDM hooks
remain the immediate recovery path; scheduled repair is the periodic fallback.

No Keenetic routes, priorities, policy rules or user configuration are rewritten.
No Telegram transport or UI changes are included in this correction.

## Validation scope

Targeted executable fixtures and the project CI gate are required before preview.
Live validation on the owner's router can cover only its current single uplink,
ppp0. USB plus Wi-Fi balancing, provider failover and a policy-only second ISP
need a representative live topology before claiming field validation.

Keenetic connection policies:
